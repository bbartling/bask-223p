# Parity: edge-microdot DuckDB vs Open-FDD NF

Comparison of the in-process DuckDB path in `examples/edge-microdot` against the Open-FDD Normal Framework app on `master` (`sql/fdd/schema/core.sql`, `sql/fdd/input_contract.json`, `sql/fdd/postgres/rules/`, and issue #1804). The edge app stays generic: no site names or equipment IDs are hard-coded.

| Area | Open-FDD NF | Edge app | Same / different |
| --- | --- | --- | --- |
| Historian / samples | Application-owned store exposed as view `fdd.input_sample(site_id, point_key, ts, value)` in SI, UTC (`input_contract.json` v3) | In-memory `fdd.sample_store` plus the same `fdd.input_sample` view; values converted to SI at ingest | **Same** contract. Physical store also keeps `value_text` and `status` for the `/history` API. |
| Bound points | `fdd.point` from `sql/fdd/schema/core.sql` (`site_id`, `point_key`, `equipment_id`, `role`, `unit`, SI scale/offset, `attrs`, …) | Same table and column names in in-memory DuckDB and in `point.parquet` | **Same** columns. DuckDB uses `JSON` instead of PostgreSQL `jsonb`. |
| Rule results | `fdd.rule_result` (status in `PASS`/`FAULT`/`INCONCLUSIVE`/`SKIPPED`/`ERROR`/`STALE`/`METRIC`, `fault_hours`, `covered_hours`, `subject_key`, window, …) | Same table and columns; upsert keeps the latest assessment per `(site_id, equipment_id, rule_id, subject_key)` | **Same** schema. `result_id` is a DuckDB sequence (`GENERATED … IDENTITY` is not available in DuckDB 2.0). |
| Tuning | `fdd.rule_config` append-only revisions, one-active unique index | Table created with the same columns; no Tuning UI or one-active partial index (DuckDB 2.0 has no partial indexes) | **Schema same, behavior different** (unused on the edge). |
| Rule file layout | `sql/fdd/postgres/rules/<rule>.sql` plus `registry.yaml` / rendered packs | `sql/fdd/rules/<rule>.sql` (`sv_stale.sql`, `sv_range.sql`, `sv_flatline.sql`, `sv_spike.sql`) | **Same convention and rule ids** (`SV-STALE`, `SV-RANGE`, `SV-FLATLINE`, `SV-SPIKE`). Edge does not vendor the full 78-rule PostgreSQL pack, helpers, or `{{PLACEHOLDER}}` renderer. |
| How rules load / run | Scheduled NF hook (rrule every 20 minutes) loads a SQL pack, builds scratch `history` / `sensor_history`, upserts `fdd.rule_result` | `EDGE_FDD_INTERVAL` (default 60s) runs every `*.sql` in `sql/fdd/rules/` against `sensor_history` and upserts `fdd.rule_result` | **Same idea, different scheduler.** Edge interval stays short for a live poller; NF is a 20-minute hook. |
| Rule inputs / aliases | Today the catalog still uses acronyms (`sat`, `mat`, …). #1804 retires them for 223P-derived snake_case (`discharge_air_temperature`, …) | `fdd.point.role` and SQL `sensor_role` are 223P-derived snake_case only; acronyms are mapped at bind time and rejected in the parity test | **Matches #1804** (ahead of NF master, which has not landed that rename yet). |
| Sweep output | `equipment_id`, `series_id`, `sensor_role`, `fault_hours`, `covered_hours` | Same columns from each edge SQL file | **Same** |
| Units | SI at the rule boundary (`degC`, `Pa`, `L/s`, …); conversion at ingest | SI at ingest and in the bundle (`degC`, `Pa`, `m3/s`, `W`, …) | **Same policy.** Edge flow unit is `m3/s` (SI); some NF flow roles are catalogued as `L/s`. |
| Export | NF Export tab: per-equipment joined CSV. Parquet appears in tutorials / `open-fdd nf pull` | `GET /api/export/bundle?hours=N` ZIP of `input_sample.parquet`, `point.parquet`, `rule_result.parquet` with the core column contracts | **Same tables/columns, different delivery.** CSV export is not implemented on the edge. `/sql` registers the three Parquet files as `fdd.*` views. |
| Persistence | Timescale / PGlite / sql.js depending on `engine`; samples are not in core.sql | `:memory:` DuckDB, rotating ZSTD Parquet snapshots (`sample_store_*.parquet`, `point_*.parquet`, `rule_result_*.parquet`) under a byte cap. Legacy `telemetry_` / `fdd_results_` snapshots still reload | **Different storage engine, same logical schema.** Snapshots are an edge/SD-card concern. |
| Engine name in results | `timescale`, `postgres-sql`, `sqlite`, `duckdb`, … | `engine = 'duckdb'` | **Compatible** |
| Config / env | NF app options: `engine`, `timescale`, hook `schedule` rrule, `history` | `EDGE_*` prefix (`EDGE_FDD_INTERVAL`, `EDGE_SNAPSHOT_INTERVAL`, `EDGE_MEMORY_RETENTION_HOURS`, `EDGE_DB_MAX_MB`, `EDGE_DUCKDB_MEMORY_MB`). `poll_seconds` on results defaults to 300 like NF | **Different names, same roles where they exist.** Edge keeps the `EDGE_` prefix so Pi `.env` files stay valid. |
| Site identifiers | `site_id` on every core row; hook is multi-site | `site_id` column is present; filled from the runtime sample `site` field (or empty). Nothing is hard-coded | **Same column, single-site deployment.** |
| SQL UI | DuckDB tutorials; in-app analytics are sql.js / PGlite | `/sql` posts read-only SQL to the in-process DuckDB. No WASM | **Edge UI** over the same schema as the NF core contract. |
| Process model | FDD hook in the NF app process (or Timescale). No shared-volume worker required | DuckDB stays **in-process** with the Microdot app. Parquet snapshots are the on-disk history | **Different process, same logical tables.** |
